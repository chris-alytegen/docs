---
title: "Errors"
description: "Stable machine-readable codes; retryable and terminal failures are distinguished — never normalize them."
---

Every error response has one shape:

```json
{ "error": { "code": "spend_cap_exceeded", "message": "…", "details": { } } }
```

`code` is **stable** — branch on it, not on the message. The SDK surfaces it as
`AlyteApiError` (`status`, `code`, `message`, `details`).

## How to treat failures

| Class | Examples | What to do |
|---|---|---|
| **Mandate refusals** | spend cap, scope, expiry, ownership | The buyer's limits said no. Surface to the buyer; **do not retry** — the answer won't change. |
| **Catalog refusals** | not on sale yet, quantity cap, geo/scheme restriction, sold out | Terminal for this request. `not_yet_on_sale` includes a `retryAfter` — schedule, don't poll. |
| **Validation** (`400`) | float prices, malformed bodies | Fix the request. Money is integer minor units, always. |
| **Auth** (`401`/`403`) | expired token, missing scope, revoked key | Re-authenticate or request the right scope. Revocation is server-side and immediate. |
| **Verification required** (`403 step_up_required`) | a [merchant-attested buyer session](/guides/buyer-sessions) tried to create or widen spending authority | Not a failure. The buyer must confirm a code sent to their email; the authorize page does this itself. |
| **Sign-in token spent** (`401 link_invalid`) | a redeem link or `session-token` exchange used twice, or after 15 minutes | Terminal for that token. Mint a new session. A refused exchange from an unregistered origin (`403`) does **not** spend the token. |
| **Browser origin refused** (`403 forbidden` on `/v1/buyer/*`) | the page's origin is not registered for the bearer's shop, the method or header is not allowed, or a sign-in/verification route was called from a partner origin | Fix the registration ([Browser access and CORS](/guides/browser-api)). Never relay sign-in or verification through your own page. |
| **Wrong verification code** (`401 code_invalid`) | the buyer typed a wrong, expired or already-used code in the consent view | Shown to the buyer by the view; they request a new code. Not an integration error. |
| **Verification delivery failed** (`502 magic_auth_send_failed` / `magic_auth_verify_failed`) | Alyte could not send or check a code with its email provider | Retryable; the view offers a retry. Not the buyer's answer. |
| **Attested consent not enabled** (`403 merchant_consent_not_enabled`) | a `merchantAttested` mint on a shop Alyte staff have not enabled for it | Terminal. Mint without `merchantAttested`, or ask about [contracted attestation](/guides/buyer-sessions). |
| **Attested ceiling exceeded** (`403 merchant_consent_ceiling_exceeded`) | the grant exceeds the configured amount/duration, uses another currency, requests recurring authority, or reuses an agent with a prior permission | Use the buyer's verification flow. Splitting the grant or revoking older grants does not reset the allowance. |
| **Payment provider key refused** (`422 psp_credentials_rejected`) | an Adyen API key sent when linking or editing a payment connection was refused by Adyen before it was stored (401: invalid key; 403: no access to the merchant account) | Terminal for that key; nothing was saved. Generate a new key on the credential that owns the client key and save again. [Connect Adyen](/guides/connect-adyen) |
| **Card setup paused** (`409 capture_unavailable`) | the shop's payment connection cannot be used for card setup right now: no public return URL on this deployment, or Adyen refuses the shop's saved API key | Terminal for the buyer; not a provider hiccup, so do not retry. The shop re-enters its key or fixes its configuration. |
| **Card preparation unavailable** (`503 card_preparation_unavailable`) | the provider could not verify a card during setup confirmation or preparation for a purchase | For setup, retry confirmation with the same setup reference. For a purchase, retain the same attempt and idempotency key and respect any retry delay. |
| **Card not authenticated** (`422 authentication_evidence_required`) | an agent tried to charge a saved card that carried no authentication evidence when it was saved (no 3D Secure, or the provider did not report the result) | Terminal for that card. The buyer saves the card again through Alyte; on Adyen the account must report the 3D Secure result ([Connect Adyen](/guides/connect-adyen#what-you-need-from-adyen)). |
| **Card not ready** (`422 card_not_chargeable`) | the card has not completed the required setup | Ask the buyer to complete or repeat card setup. |
| **Wrong card customer** (`409 card_customer_mismatch`) | the payment method is attached to a different provider customer | The buyer needs a card saved under the correct customer; changing the request's buyer identity is not a fix. |
| **Edited out from under you** (`409 commerce_schedule_conflict`) | a location, an event's venue binding or a sale-window edit carried a revision that is no longer current | Reload, re-apply the change and retry. Nothing was written. [Shared inventory and locations](/guides/shared-inventory) |
| **Inventory busy** (`409 inventory_busy`, `details.retryable: true`) | deleting a tier, event or shop collided with a purchase or release touching the same stock | Retry shortly. The deletion rolled back whole; a possibly-paid ticket is never erased. |
| **Catalogue too large** (`413 catalog_too_large`) | an inventory observation or location list would exceed 2,000 rows in one relation | No partial result is returned. Split the shop, or contact Alyte. |
| **Waiting for an access window** (`409 access_waiting`, `details.retryAfter`) | the buyer is not yet inside an [early-access window](/guides/access-rules) or the general sale | Nothing was charged. Retry at `retryAfter` with the same idempotency key. |
| **Access settings changed** (`409 access_conflict`) | a rule, its preview or a tier's general-sale time changed since you read it, or the tier has scheduled windows | Refresh, review again, and send with a new request ID. Cancel windows before moving general sale. |
| **Access view too large** (`413 access_catalog_too_large` / `access_preview_too_large`) | more than 200 rules or 100 programs in one list, or more than 2,000 queued requests in one preview | No partial result is returned. Contact Alyte. |
| **Access rules unavailable** (`503 access_unavailable` / `access_preview_unavailable`) | the shop's storage cannot serve access rules or a preview right now | Retry later. Nothing changed. |
| **Rate limited** (`429 rate_limited`) | too many requests, sign-in links or verification codes | Retryable. Wait `retryAfter` seconds (also sent as the `Retry-After` header), then retry. A `429` without `retryAfter` came from a payment provider: back off. |
| **Card / connection mismatch** (`409 instrument_provider_mismatch`) | a saved card is used at a shop or payment connection it was not saved for | Terminal. Cards are saved per shop and per payment connection; the buyer adds a card for this shop. |
| **Payment pending** (`202`) | the payment provider accepted the payment but confirms it asynchronously | Not a failure and not a success yet. **Do not submit the payment again.** Wait for the settlement webhook or poll the payment. |
| **Indeterminate payment outcomes** | PSP timeout mid-charge | The charge may have succeeded. Alyte **halts rather than guesses** — it will never retry a possibly-succeeded charge into a double-charge, and neither should you. Re-check the payment's status; your `idempotencyKey` makes a safe re-confirm possible. |

## The two rules that matter

1. **Idempotency**: send a stable `Idempotency-Key` on every confirm. It is the
   reason a timeout is an inconvenience instead of a double charge.
2. **Don't normalize errors**: a hard decline and a retryable network blip are
   different codes on purpose. Collapsing them into one generic failure is how
   retry storms happen.
